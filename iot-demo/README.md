# ZPR x Oracle IoT Demo

Create a demo that leverages the ZPR reference implementation to control traffic from IoT
devices to the Oracle IoT Platform. Two MQTT devices publish telemetry through a ZPR
network to the Oracle IoT Platform; policy allows device-a and blocks device-b.

The demo runs on three OCI compute instances — see
[oci-compute/TOPOLOGY.md](oci-compute/TOPOLOGY.md) for the diagram and port matrix. A
single-laptop variant (9 terminals) is in [setup/README.md](setup/README.md).

## Prerequisites

- **OpenTofu** (`tofu`) and the **OCI CLI** (`oci`) on `$PATH`, with an `~/.oci/config`
  profile `DEFAULT` for the ZPR-IoT-Demo tenancy.
- **Docker** — the OL9 build runs `sudo docker`, and the local egress adapter runs in
  Compose. The build container needs outbound network *and* git access to GitHub
  (`zpr-visaservice` pulls `zpr-common` from a git tag).
- **SSH keypair** at `~/.ssh/zpr-demo`; the public half is injected into the instances.
  `ssh-keygen -t ed25519 -f ~/.ssh/zpr-demo -N ""` if missing.
- **Local checkouts** of `zpr-core`, `zpr-visaservice`, and `zpr-compiler`.
- **Rust toolchain** for the local `vs-admin` and `zplc` builds (the OL9 build installs
  its own inside the container).

## Environment variables

Nothing here hardcodes a source path. Four variables locate everything; set them once in
`oci-compute/sources.env` (gitignored):

```bash
cp oci-compute/sources.env.example oci-compute/sources.env
$EDITOR oci-compute/sources.env
```

| Variable | Points at | Required | Used by |
|---|---|---|---|
| `ZPR_CORE_SRC` | `zpr-core` checkout — builds `ph` | yes | `build-in-ol9.sh`, egress Compose, `setup/` runbook |
| `ZPR_VS_SRC` | `zpr-visaservice` checkout — builds `vs`, `vsapikey`, `vs-admin` | yes | `build-in-ol9.sh`, `vs-admin.sh`, `setup/` runbook |
| `ZPR_COMPILER_SRC` | `zpr-compiler` checkout — builds `zplc` | for policy compiles | you, by hand |
| `ZPR_BUILD_DIR` | OL9 build output; defaults to `$HOME/.cache/zpr-oci-build` | no | `build-in-ol9.sh` |

Two layouts are supported. Split repos:

```bash
ZPR_CORE_SRC=$HOME/src/zpr-core
ZPR_VS_SRC=$HOME/src/zpr-visaservice
ZPR_COMPILER_SRC=$HOME/src/zpr-compiler
```

A monorepo with the components as subdirectories:

```bash
ZPR_CORE_SRC=/home/othomas/zpr/core
ZPR_VS_SRC=/home/othomas/zpr/visaservice
ZPR_COMPILER_SRC=/home/othomas/zpr/compiler
```

`sources.env` only sets what is unset, so an exported variable still wins for a one-off:
`ZPR_VS_SRC=~/src/zpr-vs-experiment ./vs-admin.sh actors`.

Everything else is derived — there is no variable for the `ph`/`vs`/`vs-admin`/`zplc`
binaries themselves. Two files consume `sources.env` indirectly rather than reading it:
`oci-compute/binaries.auto.tfvars` (generated by the build) and `setup/egress/.env`
(generated by `gen-env.sh`). Both are gitignored; neither should be hand-edited.

## Compile the policy (manual)

**`setup/iot-demo.bin2` is committed to the repo but built by no script.** It has to be
compiled by hand with `zplc`, and the compiler version matters: `zplc` 0.13.0 began
*rejecting* `endpoint.*` classnames that earlier versions accepted, and a `.bin2` from a
mismatched compiler either fails to build or is refused by `vs` at load. Because the
artifact is checked in, the failure is silent — you can deploy a `.bin2` compiled months
ago by a different compiler and get no warning at all.

`zpr-compiler` and `zpr-visaservice` are versioned together (both 0.14.0 at time of
writing); `zpr-core` versions independently (0.6.0).

So, whenever the `vs` you deploy changes version:

```bash
# 1. Check out the zpr-compiler tag matching your vs, and build it.
cd "$ZPR_COMPILER_SRC" && cargo build --release

# 2. Run it FROM setup/ — iot-demo.zplc references key PEMs by relative path
#    (node/, vs/, device-a/, device-b/, egress/), so any other cwd fails on a
#    missing key file.
cd <this repo>/iot-demo/setup
"$ZPR_COMPILER_SRC/target/release/zplc" iot-demo.zpl -c iot-demo.zplc
```

That writes `iot-demo.bin2` beside the input. Repeat for `iot-demo-deny.zplc` if you use
the deny-policy variant. Commit the regenerated `.bin2` with the compiler version in the
commit message so the artifact's provenance stays recoverable.

Unresolved: whether this demo's policy is signed (`zplc -k <private key>`, presumably
`setup/authority/auth-ca.key`). Nothing in `setup/vs/vs-conf.toml` requires a policy
verification key, which suggests not. Confirm on your first real compile and record the
exact command here.

## Getting started

```bash
# 1. Configure source paths
cp oci-compute/sources.env.example oci-compute/sources.env && $EDITOR $_
. oci-compute/sources.env

# 2. Compile the policy (above) — do this BEFORE the build, while a stale
#    .bin2 is still something you're thinking about.

# 3. Build ph/vs/vsapikey for Oracle Linux 9 (~10 min first run).
#    Also writes oci-compute/binaries.auto.tfvars, which tofu loads automatically.
./oci-compute/build-in-ol9.sh

# 4. Build the local admin client (plain debug build; never ships to an instance)
(cd "$ZPR_VS_SRC" && cargo build -p vs-admin)

# 5. Set operator_cidr in oci-compute/terraform.tfvars to your public IP /32
#    (there is a TODO sitting in that file right now).

# 6. Apply the OCI IoT platform stack first — oci-compute reads its outputs
tofu -chdir=oci-iot init && tofu -chdir=oci-iot apply

# 7. Apply the compute stack
tofu -chdir=oci-compute init && tofu -chdir=oci-compute apply

# 8. Wait for cloud-init, then bring the demo up
CORE=$(tofu -chdir=oci-compute output -raw zpr_core_public_ip)
ssh -i ~/.ssh/zpr-demo opc@$CORE 'sudo cloud-init status --wait'
./oci-compute/post-init.sh        # one-time: egress addr + return-path routing
./oci-compute/start-device-a.sh   # the ZPR-allowed device
./oci-compute/start-device-b.sh   # the ZPR-blocked device
```

Then verify with `./oci-compute/preflight.sh`, and drive policy live with
`./oci-compute/attribute.sh` and `./oci-compute/vs-admin.sh`. Full walkthrough and
expected output: [oci-compute/README.md](oci-compute/README.md).

## Common first-run failures

| Symptom | Cause |
|---|---|
| `GLIBC_2.38 not found` on an instance | binary built outside the OL9 container — run `build-in-ol9.sh` |
| build fails fetching `zpr-common` | container has no network or no git access to GitHub |
| `cargo build --locked` fails | `Cargo.lock` is stale in a checkout; update and commit it there |
| `vs` rejects the policy, or `zplc` errors on a classname | `.bin2` compiled by a mismatched `zplc` — recompile (above) |
| tofu: `No value for required variable "ph_binary_path"` | `build-in-ol9.sh` hasn't run, so `binaries.auto.tfvars` doesn't exist |
| `vs-admin` 401s | cached `.vs-admin.key` went stale after a destroy/reapply; `vs-admin.sh` re-fetches it, so check cloud-init keygen ran |
| Compose: `ZPR_CORE_SRC — run ./gen-env.sh` | `setup/egress/.env` missing or predates this change |
